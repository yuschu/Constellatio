## 一、结论先行

1. **"替换首页"是产品形态变更，不是视觉重构。** 现有首页是看板（`plugin_host/templates/home_dashboard.html`，267 行、4 张指标卡 + 趋势大盘 + 快捷发起 + 插件运维 + 公告 + 消息）。替换后用户第一屏变成对话区 + 侧栏，**看板承载的信息必须重新找到出口**，否则是功能退步。§4.4 给了三种安置方案。
2. **"模型可插拔"这一条，把原方案里最大的成本项消掉了。** 上一轮判断"接本地模型"与"不引入新运行时依赖"冲突——现在改成宿主只提供 **OpenAI 兼容接口的客户端**（用标准库 `urllib.request`，零新增依赖），具体跑哪个模型变成**部署时的配置**，不是代码依赖。用户可以在自己机器上跑 ollama / llama.cpp server / vLLM / 任何兼容服务，也可以填公司内部网关。"离线"从硬约束降级为可选部署形态。
3. **A 阶段就能交付可用价值，且风险最低。** A 只读不写，模型即使判断错也只是查错数据，可重来。B 加人工确认闸门。C 才碰真实写操作，那时才需要把权限与审计接进工具层。

### 2.2 复刻成本修正

上一轮按 1398 报的"4–5 倍于现有首页"，**偏高了**。实际可分三层看：

- **可见框架 ≈ 423 元素**（271 侧栏 + 106 主区 + 46 底栏）。这是必须手写的那部分，约 **10 个组件模板**就能覆盖。

**净结论：框架 + 对话组件合计约 16–18 个模板**，不是我上一轮按 1398 元素估的"4–5 倍于现有首页"。这个修正对排期有直接影响——它把这件事从"另一个项目"降到"一个迭代铺框架 + 分阶段填组件"。真正需要警惕的不是元素数量，是 §4 C 阶段那个 48% 的准确率问题，那是能力问题，不是工作量问题。

## 三、架构设计

### 3.1 做成 `plugins/assistant`，不硬改宿主

```
plugins/assistant/
├── apps.py          # 注册 + 首页接管声明
├── models.py        # Conversation / Message / ToolCallLog
├── llm.py           # 模型适配层（唯一出网点，urllib）
├── tools.py         # 工具注册表（按角色过滤）
├── views.py         # 对话接口 + 首页视图
├── urls.py
├── registry.py      # 向宿主注册"我可提供首页"
├── templates/assistant/
│   ├── home_chat.html      # 对话式首页
│   └── _message.html       # 消息气泡片段
└── static/assistant/css/   # 消费 dsh-visual-spec 的 token
```

两条硬纪律：

- **`llm.py` 是本插件唯一的出网点**，其它模块一律不得直接发 HTTP。这样"离线"这件事只有一个开关位置。
- **`tools.py` 里每个工具必须声明 `required_permissions`**，调用前按当前用户过滤。C 阶段的越权防线在这里，不在模型侧。判定直接复用 `registry._user_perm_codenames(user)`——它已经把「未登录 / `permission_frozen` / 停用 → 全拒绝」「超管 → 全放行」「其余 → 基线 + 个人 + 角色并集」这套语义写全了，`get_menus` 也走同一口径。**不要为 AI 另造一套权限判定**，否则两套口径迟早打架。

> 工具调用的完整实现——前置条件、一次调用的完整链路、工具 schema、服务端校验层、执行循环代码、A/B/C 差异、失败兜底——见 **`docs/ai-tool-calling.md`**。其中服务端校验层是这套实现里最不能省的一层：4B 级模型的 `arguments` 经常不是合法 JSON，直接 `json.loads` 后不校验就执行会出事。

### 3.2 首页接管机制（宿主层最小改动）

现有 `plugin_host/registry.py` 的 `PluginMeta` **没有**任何"首页"概念（字段只有 `name / version / title / menus / permissions / urls / signals / templates / app`）。要接管首页，必须扩一个字段。改动如下，全部向后兼容：

```python
# plugin_host/registry.py
class PluginMeta:
    def __init__(self, name, version, title=None, menus=None, permissions=None,
                 urls=None, signals=None, templates=None, app=None,
                 home_provider=None):            # ← 新增，默认 None
        ...
        self.home_provider = home_provider       # 可调用对象：request -> HttpResponse


def get_home_provider():
    """返回唯一一个声明了 home_provider 且插件开关为 enabled 的实现。

    多个插件同时声明时取 PLUGIN_REGISTRY 顺序的第一个并打 warning ——
    "谁的首页生效"必须是确定的，不能随插件加载顺序漂移。
    """
    for key, meta in PLUGIN_REGISTRY.items():
        if meta.home_provider and plugin_enabled(key):
            return meta.home_provider
    return None
```

`plugin_enabled(key)` 已经实现了「DB 开关优先 → 静态 `OA_PLUGINS` → 默认 True」三级判定，直接复用，不新造开关逻辑。

宿主视图只加一次查询、不改任何既有分支：

```python
# plugin_host/views.py
def index(request):
    provider = registry.get_home_provider()      # 返回 None 则走原逻辑
    if provider is not None:
        return provider(request)
    # ... 原有看板逻辑一行不动
```

**降级路径明确**：没装插件 / 开关关闭 / `home_provider` 为 None / 模型未配置 → 全部回落原首页，零风险。

**查询成本要注意**：`get_plugin_switches()` 每次调用都读表（v1.7.13 明确删掉了进程内缓存，因为多 worker 下会残留旧快照）。首页本来已有 6 次开关表查询，加这一次变 7 次。若在意，可在 `index` 开头取一次 `get_plugin_switches()` 快照后把 `plugins` 透传给后续调用，但那是既有待办（roadmap 第 10 条查询合并），本次不顺手做。

**顺带补上主线缺口**：首页接管第一次成为插件能力，之后任何插件都能提供首页变体。目前首页和 `workbench.py`（13.6 KB 数据聚合）都硬编码在宿主层，这是"万物皆可插件"主线上的一个未闭环处。

### 3.3 模型适配层

只实现 OpenAI 兼容协议一种，覆盖绝大多数本地与自建服务：

| 用户可选的后端 | 说明 |
|---|---|
| ollama | 本地默认，`/v1/chat/completions` 兼容 |
| llama.cpp server | 单文件二进制，Q4 GGUF 直接跑，最轻 |
| vLLM / SGLang | 有 GPU 时性能最好 |
| LM Studio | 图形界面，适合非技术客户 |
| 公司内部网关 | 任何暴露 OpenAI 兼容路径的服务 |

配置项（全部存数据库，管理员在插件配置页填；已落地，见 `docs/ai-assistant-config.md`）：

```
base_url        例 http://127.0.0.1:11434/v1
model           例 qwen3:4b
api_key         可空（本地服务通常不校验）
timeout_seconds 默认 240（内置 CPU 4B）
max_tokens      默认 1536
```

**"内置模型"的落地含义（2026-11-14 调整）**：Constellatio 在 Compose 里内置 `ollama` 服务与 `ollama-init`，首次启动自动把 `qwen3:4b` 拉进 `ollama_data` 卷（约 2–3 GB）；Web 默认连 `http://ollama:11434/v1` + `qwen3:4b`，开箱即用。模型与 Web 镜像分离，不把权重烘焙进应用镜像；配置页仍保留，管理员可改成公司网关、GPU 机器或更大模型。首次拉取需要联网；官方源最多等 `OLLAMA_PULL_TIMEOUT`（默认 300 秒），失败或超时自动切 ModelScope 非思考版回退（`Qwen3-4B-Instruct-2507-GGUF:Q4_K_M`），回退件拉下来后 `ollama create` 成同名 `qwen3:4b`（`num_ctx 4096`、`num_predict 1536`）。拉取完成后 `ollama-init` 会做一次最小生成预热，把 4B CPU 冷加载的 30–45 秒放在启动阶段。Compose 默认 `ASSISTANT_LLM_TIMEOUT=240`、`ASSISTANT_LLM_MAX_TOKENS=1536`：官方件 CPU 生成约 7 token/s，一次带工具调用的问答实测约 3 分钟，120 秒会在思考段未结束时被掐断；官方模板不认 `reasoning_effort=none`，客户端会把 `</think>` 之前的推理段剥掉，只把答案给用户。回退件模板支持 `reasoning_effort=none` 关闭思考，单轮约 3–5 秒。`web` 等 `ollama-init` 成功后才启动，拉取失败时先看 `ollama-init` 日志，不会出现“服务在、模型没到”的半可用状态。

**档位选择（已定：部分客户有 GPU）**：

代码层不区分档位，只认 `model` 这个字符串。真实差异体现在部署时填什么：

| 客户环境 | 建议填写 | 预期速度 | A 阶段能否达标 |
|---|---|---|---|
| 纯 CPU，4–8 核 | `qwen3:4b`（Q4，约 2–3 GB） | 5–12 t/s | 按 70% 阈值验收 |
| 有 GPU 8 GB 级 | `qwen3:8b`（Q4，约 5–6 GB） | 20–40 t/s | 按 85% 阈值验收 |
| 有 GPU 12 GB+ | `qwen3:8b` 或 `qwen3:14b`（Q4，约 9 GB） | 20–40 t/s | 85%+ |

**验收阈值按最低档（4B / 70%）设**。理由：这是"部分客户有 GPU"的必然推论——同一套代码要交付给有 GPU 和没 GPU 两类客户，验收必须覆盖最差环境。达不到 70% 就说明必须抬到 8B，这本身是个干净的决策信号，而不是模糊的"效果不太好"。

**配置页要做连通性自检**：填完 `base_url` + `model` 后点“测试连接”，发一条最短的 chat 请求（如“回复 OK”），显示 ① 是否连通、② 首 token 延迟、③ 是否为本机/内网地址。三项都在配置页可见，用户不用自己猜。**已落地**；当前客户端非流式，延迟展示整轮请求耗时，不冒充首 token 延迟。

### 3.4 看板安置（已定：侧栏槽位 + 独立页）

**决策（2026-11-12 负责人已定）：看板保留，入口放在侧栏顶部功能入口区。**

对齐位置是 DSH 侧栏那排「新会话 | 插件 | 自动化任务 | 更多」——实测这排入口在侧栏 `bhn1Oq_groupSection` 三个分组内，宽 280px 的侧栏顶部。OA 的"看板"放同一位置，即侧栏顶部一排功能入口中的一个。

**落地成本比预想低**：`PluginMeta.menus` 本来就支持菜单项声明 `{'label', 'icon', 'url', 'perm'}`，`get_menus(user, plugins)` 已经做了 RBAC 过滤。所以只需在插件注册时加一条菜单：

```python
menus=[{'label': '看板', 'icon': 'grid', 'url': '/dashboard/', 'perm': 'dashboard_view'}]
```

侧栏渲染逻辑一行不用改，权限过滤自动生效。

**页面本身**：新增 `/dashboard/` 路由承载原 `home_dashboard.html`，**原模板一行不动**。改造期间它自带 A/B 对照——用户可以在"对话首页"和"看板页"之间来回，不合适就切回默认。

| 原首页六块信息 | 出口 |
|---|---|
| 待我审批 | 侧栏待办计数（红点）+ 对话区卡片 + 看板页 |
| 考勤概况 | 看板页 |
| 流程发起 | 看板页 |
| 插件运行状态 | 看板页 |
| 公告简报 | 侧栏入口 + 看板页 |
| 我的消息 | 侧栏未读红点 + 看板页 |

**唯一不能省的**：侧栏必须有**待办计数红点**。用户早上打开系统是要知道"有没有事等着我"，这一条丢了就是功能退步。

### 3.5 对话记忆与能力优化

**已定（2026-11-12）：对话记忆保存在本地数据库。** 这推翻了本文早先"A 阶段先不入库"的建议，按负责人要求改为入库。

表结构最小集：

```
Conversation                     Message
├─ user        FK → AUTH_USER   ├─ conversation  FK
├─ title       首条消息摘要      ├─ role          user / assistant / tool
├─ created_at                   ├─ content
└─ updated_at                   ├─ tool_calls    JSON（A 阶段为空）
                                ├─ tokens_in / tokens_out
                                └─ created_at
```

沿用现有约定：继承 `AuditModel` 自动填审计字段；`(user, updated_at)` 建索引供侧栏会话列表排序。

**"根据每次对话优化模型能力"存在四档完全不同的实现，代价差两个数量级**，需要负责人明确要哪一档（§六 待确认）。四档从轻到重：

| 档 | 做法 | 解决什么 | 增量代价 |
|---|---|---|---|
| **L1 原样回放** | 把最近 N 条消息拼进 prompt | 多轮连续 | 已在 A 阶段 |
| **L2 摘要压缩** | 超长时用模型自己浓缩历史 | 上下文窗口不够 | 小（多一次模型调用） |
| **L3 术语对齐** | 从系统数据自动生成术语表；用户新说法经确认后并入 | **"越来越懂公司术语"** | 中（见 §3.5.1） |
| **L4 权重微调** | 用对话数据 LoRA/QLoRA 训练模型 | 能力真提升 | **大（等于一个新项目）** |

**L4 为什么不该放进 OA**：

- 训练要 GPU（8B QLoRA 至少 12–16 GB 显存），客户现场通常没有。
- 要几百条清洗过的样本，还要一份独立评估集——否则训完不知道好没好。
- **灾难性遗忘**：小模型微调后通用能力明显下降，而 OA 场景恰恰要求它什么都能答一点。
- **每客户一版模型文件**：交付时不同客户的权重不一样，版本管理与回滚无从下手。
- **不可回滚**：训练坏了没有基线可比。

**结论建议**：L1+L2+L3 组合，L4 明确不做（至少不作为 OA 内置能力）。L3 是性价比最高的一档——它不需要训练，只需要一份"高质量示例库"，而且能做到可解释、可人工纠偏、可随时清空。

**一个必须说清的数据流向问题**：对话存本地 ≠ 数据不出本机。只有当 `base_url` 指向 `127.0.0.1` / 局域网地址时才是真离线；如果用户填的是公网网关或云端地址，**每一句对话都会带着业务数据离开这台机器**。所以插件配置页要显式显示当前连接的是不是本机/内网地址，不要只让用户填个 URL 就完事。

#### 3.5.1 术语对齐怎么做（不训练、不靠模型泛化）

"越来越懂公司术语"最有效的实现**不是 few-shot，也不是微调**，而是**确定性术语映射 + 模型兜底**。理由：术语是有限、可枚举、有权威来源的，不该让模型去猜。

**术语源（已实测，全部可自动枚举）**：

| 来源 | 字段 | 规模 |
|---|---|---|
| 审批类型 | `Approval.Type`（`TextChoices`），`get_approval_type_display()` 拿显示名 | 个位数 |
| 部门 | `user.Department.name`（`unique=True`） | 十几到几十 |
| 角色 | `user.Role.name`（`unique=True`） | 个位数 |
| 功能菜单 | `PluginMeta.menus` 的 `label` | 十几个 |
| 人员姓名 | `user.User.last_name` | 随规模增长 |

**生成方式**：每次会话开始时扫一遍，不缓存（数据量小，一次查询的事）：

```python
def build_glossary():
    """从系统现有数据生成术语表：术语 → 结构化参数。"""
    g = {}
    for value, label in Approval.Type.choices:          # "报销" → approval_type=EXPENSE
        g[label] = {'tool': 'search_approval', 'args': {'approval_type': value}}
    for name in Department.objects.values_list('name', flat=True):
        g[name] = {'tool': 'query_department', 'args': {'department': name}}
    for name in Role.objects.values_list('name', flat=True):
        g[name] = {'tool': 'search_user', 'args': {'role': name}}
    return g
```

**判定顺序（关键）**：

```
用户输入
  ↓
① 术语表精确命中？ → 直接构造工具参数，跳过模型（100% 准，零 token）
  ↓ 未命中
② 别名表命中？（"差旅单"→"报销"这类人工/学习得来的说法）
  ↓ 未命中
③ 交给模型做意图识别和参数填充（兜底）
```

**这一步的价值**：把最常问的那几十个词从"模型推理"降级成"查表"。模型准确率 48% 的短板，在术语表覆盖的范围内直接不存在。

**"根据每次对话优化"的真实落点在这里**：

```
用户："帮我看看差旅单的进度"
系统：术语表没有"差旅单" → 走模型 → 模型推测是 EXPENSE → 返回结果
用户：纠正 or 点"是"确认
系统：把"差旅单 → EXPENSE"写进别名表
用户下次再说"差旅单" → ① 直接命中，不再走模型
```

这才是"越用越懂"的正确形态：**增量是一个别名映射，不是一份权重**。它可解释（配置页能看到学到的所有别名）、可纠正（点一下删掉）、可回滚（清空别名表就回到出厂状态）。

**为什么不做 few-shot 注入**：few-shot 靠模型自己从示例里泛化，小模型泛化能力弱，效果不稳定且不可解释；术语映射是确定性的，同样的输入永远同样的输出。

### 3.6 语义检索（已授权放宽依赖）

负责人已同意为语义检索放宽依赖。但**先算一下到底需不需要真加依赖**：

**用同一个模型服务拿嵌入向量**，不额外部署嵌入模型——ollama / vLLM / llama.cpp server 都提供 `/v1/embeddings`：

```
POST {base_url}/embeddings
{"model": "{model}", "input": "差旅单的进度"}
→ {"data": [{"embedding": [...768 个浮点数...]}]}
```

**存储**：`Message.embedding` 用 `JSONField` 存裸数组，不引任何向量库。

**检索规模测算（2026-11-12 已决定"对话一直留存"，按此重算）**：

先分清两类数据——**文本是原始数据，向量是派生数据**。原话"一直留存"约束的是前者，后者可以随时重建，所以可以有界。

| 场景（只嵌入用户消息） | 条数 | 文本 | 向量 f32 | 向量 int8 |
|---|---|---|---|---|
| 30 人 × 3 轮/天 × 1 年 | 32,850 | 11 MB | 96 MB | 24 MB |
| 50 人 × 5 轮/天 × 3 年 | 273,750 | 94 MB | **802 MB** | 201 MB |
| 50 人 × 5 轮/天 × 5 年 | 456,250 | 157 MB | **1337 MB** | 334 MB |
| 100 人 × 5 轮/天 × 5 年 | 912,500 | 313 MB | **2673 MB** | 668 MB |

**永久留存的文本毫无压力**（50 人 5 年才 157 MB，一条 120 字中文的存储成本可以忽略）。**永久留存向量则不行**——50 人 5 年 f32 要 1.3 GB，100 人要 2.6 GB，而且纯 Python 遍历 45 万条余弦要 7 秒以上。

**所以采用「文本全留 + 向量滚动」**：

| 数据 | 留存策略 | 理由 |
|---|---|---|
| **消息正文**（`Message.content`） | **永久留存，不清理** | 便宜；用户随时可翻历史 |
| **会话摘要**（`Conversation.title` / 摘要） | 永久留存 | 几百字节，用来给老会话做检索入口 |
| **向量**（`Message.embedding`） | **只给近 90 天建，滚动淘汰** | 派生数据，可重建；有界后规模封顶 |
| 老会话的向量 | **按需回填**：用户点开某个老会话时才补算 | 不预先算，避免冷数据占空间 |

**滚动窗口的规模封顶**（90 天）：

| | 条数 | 向量 f32 | 向量 int8 |
|---|---|---|---|
| 10 人 × 3 轮/天 | 2,700 | 7.9 MB | 2.0 MB |
| 50 人 × 5 轮/天 | 22,500 | **65.9 MB** | 16.5 MB |
| 100 人 × 5 轮/天 | 45,000 | 131.8 MB | 33.0 MB |

**50 人的中型客户封顶 66 MB、2 万条、单次检索 0.5 秒以内**——这个规模纯 Python 全量 cosine 完全够，`numpy` 都不用加。

**3 年前的对话靠什么找**：不是语义检索，是「会话列表 + 标题关键词 + 时间筛选」。这符合实际用法——人回忆老对话是"3 月那次关于报销的"，不是"跟那次差不多的"，关键词就够。老会话真要参与语义检索，点开时补算向量即可。

**结论**：`numpy` 这个唯一被授权的依赖，**在 A/B 阶段依然用不上**。它在 2 万条以上才有意义，而滚动窗口把规模封在 2 万条附近。

**嵌入的分层策略**（省 token 和磁盘）：

| 层 | 是否嵌入 | 理由 |
|---|---|---|
| 用户消息 | 是 | 检索主要靠用户怎么问 |
| 助手回答 | 否 | 回答是生成物，检索价值低且体积大 |
| 工具调用记录 | 是（仅参数摘要） | "上次查的是哪个部门"这类需要 |

**检索触发的时机**：只在用户话里出现指代（"上次那个""之前提过的""刚才说的"）时才做检索，其余情况只带最近 N 条。**不做每轮全量检索**，既省时延也省 token。

## 四、A → B → C 阶段定义

### A 阶段：只读助手（1 个迭代）

**能力**：自然语言 → 只读查询。模型只做一件事：把用户的话翻译成工具调用参数，**执行权在后端**。

```
用户："这个月我批了几个单？"
模型 → 调用 stats_approval_count(month=2026-11, user=self)
后端 → 校验权限、执行 ORM 查询、返回数字
模型 → "本月你审批通过 12 单，驳回 2 单。"
```

**A 阶段工具集（全部只读，6 个）**：`search_approval`、`stats_approval_count`、`stats_attendance`、`list_notice`、`query_department`、`search_user`。

**B 阶段新增**：`draft_approval`（也只读、不写业务库，把请假/报销/用章/外出/加班/调休六类字段整理成草稿）。

**验收标准**：
- 20 条固定问句，意图识别 + 参数正确 ≥ 70%（4B 级模型的现实天花板，达不到就换 8B）。验收集与评分命令见 `docs/ai-assistant-eval.md`；**4B 19/20（95.0%）已达标**，9B 参考 19/20。
- 任何情况下不产生写操作（代码层断言：A 阶段工具集里不存在 `update/delete/create`）
- 模型服务不可达时，3 秒内降级为"助手暂不可用"，页面其余部分正常
- **CSP 零违规**（对话流全部走服务端渲染 + 外部 JS，不内联）

**回滚**：关掉插件开关即回落原首页，数据表留着不影响任何东西。

### B 阶段：建议-确认（2–3 个迭代）

**能力**：生成草稿，**一律人工点确认才执行**。

```
用户："帮我起一张出差报销"
模型 → 读取可用表单类型、填出草稿字段
界面 → 渲染成一张"待确认卡片"，字段可编辑
用户 → 点"提交"
后端 → 走原有审批创建逻辑（权限、审计完全复用）
```

**关键设计**：草稿提交走的是**原有视图函数**，不是新写一条写库路径。这样审批的整套权限与审计自动继承，**不需要为 AI 单独做一套安全机制**。

**验收标准**：
- 草稿字段完整率 ≥ 80%，用户平均修改字段 ≤ 2 个
- 提交必须经过真实 HTTP POST 到原审批创建端点（测试断言请求路径）
- 模型生成的字段必须在界面上可编辑，不允许"生成即提交"

**本轮落地（六类草稿，2026-11-14）**：
- 工具：`draft_approval` 接受 `leave` / `expense` / `seal` / `outing` / `overtime` / `comp`；时间规范化到 `YYYY-MM-DDTHH:MM` / `YYYY-MM-DD`，金额用 `Decimal` 量化两位；缺时间、金额或起止时间时返回 `missing`，不猜；结束时间必须晚于开始时间；工具注册 `write=False`，不创建 `Approval`。
- 卡片：助手消息的 `tool_calls` 提取最后一份有效草稿，首页渲染**可编辑草稿卡片**——请假、报销、用章、外出、加班、调休字段按类型直接在卡片里改；用章卡片带文件选择；调休卡片从本人已通过的加班单里选依据；部门/审批人取 `candidate_approvers` / `fallback_approvers` 同源默认值，以隐藏字段随表单提交。卡片不自动提交。
- 桥接：卡片「去审批表单调整」进入 `/plugins/assistant/draft/<message_id>/`，只有当前用户会话下、且 `approval_view` 才可读；草稿放 session 的 `assistant_approval_drafts`（随机 token，最多 5 份），302 到 `/plugins/approval/new/?type=...&draft=...`。
- 提交：卡片表单直接 POST 原 `approval_create`，隐藏 `approval_type` / `draft` / `department` / `approver`；`approval_create` 校验字段、建单并 `submit()`，成功后清 token。没有新增数据库迁移或审批写入口。
- 真实验证：正式栈官方 `qwen3:4b` 对“帮我请个假，明天上午九点开始，事由家里有事”返回 `2026-11-15 09:00` / “家里有事”；`tool_calls` 落库 `duration_ms=103`；首页与草稿链接 HTTP 200/302，原表单 200 且预填。六类扩展后，正式栈对“明天晚上六点到九点加班，事由版本上线”返回 `2026-11-15 18:00`~`21:00` / “版本上线”，`draft_approval` 成功且 `Approval` 新增 0；容器内真实数据库渲染六类卡片 6/6，用章文件、调休依据、外出/加班事由字段均命中。POST 建单由测试覆盖；正式库另在事务内通过原端点 POST 六类，全部 302、token 清除、`form_data` 正确，回滚后 `Approval` 48→48，用章附件无残留。随后用 `mkt_chu` 逐条真机补测报销、用章、外出、调休：前三类草稿均生成，日期分别为 `2026-11-14` / `2026-11-16T10:00` / `2026-11-16T09:00`~`12:00`（容器当时本地日期为 2026-11-15，相对说法与结果一致）；调休对“下周一下午”只返回 `missing=['开始时间','结束时间']`，未猜具体时段；四类均 `Approval` 新增 0。
- 相对日期：提示词规则 9 要求把今天/明天/昨天/后天/下周几先换算成具体日期再调用工具，换算不确定就追问；系统提示同时给出当天星期几，避免模型把 2026-11-15（星期日）误认成星期二。正式栈复测“下周一上午九点到下午六点调休”返回 `2026-11-16T09:00`~`18:00`；“下周一下午调休”不调用工具，直接追问具体起止时间。
- 调休时段口径：用户只说“上午/下午/晚上”但没有具体钟点时，`draft_approval` 返回 `missing` 并追问具体起止时间，不自行补成 09:00–12:00 / 14:00–18:00 之类的默认区间，避免把猜测带进审批单。
- 评价缺口：六类草稿均已支持；草稿完整率与平均修改字段数未做统计，留待积累真实会话后再评。

### C 阶段：对话操作（独立项目，不建议在设计阶段承诺排期）

**能力**：直接调工具写库。

**这一阶段的安全底线（不可协商）**：

1. **工具集按角色过滤**，权限判定在 `tools.py` 的服务端代码里，不看模型怎么说。
2. **每个写操作写审计**，审计人字段填 `当前用户（经 AI 助手）`，`blockchain` 插件的留痕链路必须覆盖到。
3. **不可逆操作必须二次确认**（删除、批量审批、跨部门操作）。
4. **意图不明确时拒绝执行**，不允许"猜一个最可能的"。

**这一阶段的真实风险**：BFCL v4 上 8B 级模型整体准确率约 **48%**（本地小模型在难任务上会更低）。48% 放在"读取"能重试，放在"写库"不可接受。所以 C 阶段要么换更大模型（14B 起，Q4 约 9 GB），要么把动作粒度压到"一次只做一件事 + 强确认"。

## 五、风险与不做

| 风险 | 处置 |
|---|---|
| 替换首页后用户找不到待办 | 方案 ② 保独立看板页；侧栏顶部放待办计数与入口 |
| 模型服务不可达导致首页挂掉 | 所有模型调用包超时 + 异常兜底；失败即降级为静态提示，首页主体毫发无损 |
| 客户机器内存不足 | 文档给出最低配置（4B Q4 约 2–3 GB / 8B Q4 约 5–6 GB），并在配置页做连通性自检 |
| CPU 推理慢（5–12 t/s） | 流式输出 + 首字延迟提示；长回答截断 |
| 审计字段被绕过 | 所有写操作复用原视图函数，不新开写库路径（B 阶段已定死这一条） |

**明确不做**：

- 不把模型权重打进 Web 应用镜像；内置模型走独立 `ollama` 服务与模型卷。
- 不引入 requests / httpx / openai SDK，只用标准库。
- 不为 AI 单独开辟写库路径。
- A/B 阶段不碰任何写操作。
- 不做多轮复杂 Agent 编排（那是 DSH 的领域，不是 OA 的）。
