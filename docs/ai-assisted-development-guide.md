# AI 辅助开发规范

> 项目：Constellatio —— 基于 Django 的企业办公自动化系统（全栈插件化）
> 文档版本：v1.5 · 2026-10-21
> 适用范围：本项目开发过程中所有 AI 辅助工具（豆包 / Copilot / Cursor 等）的使用行为
> 关联文档：constraints-and-acceptance.md（硬约束）、development-guide.md（开发规范）

---

## 一、角色定位

1. **AI 是辅助者，不是决策者**：技术决策、架构变更、验收结论一律由项目负责人确认
2. **代码所有权归项目**：AI 生成的代码必须经人工 review 后才合入
3. **不承诺，验证才算数**：任何"改好了 / 能跑了"必须有测试或运行结果支撑，禁止用"应该没问题"代替验证

## 二、硬性禁止（红线）

1. 不得擅自更改已定版技术栈与架构（见 constraints-and-acceptance.md）——如禁止引入 Vue/React、禁止替换数据库默认引擎
2. 不得引入未经批准的第三方依赖（每次新增依赖须先确认）
3. 不得跨插件直接 import 对方 models/views（插件间通信只走 signals）
4. 不得绕过插件契约（PluginMeta 字段缺一不可）
5. 不得覆盖、删除、重命名未经确认的文件与代码
6. 不得编造数据、来源、测试结果；不得伪造验证通过
7. 不得静默降级交付（把应完成的功能改成教程/模板/让用户手动操作）
8. 不得在未说明风险前执行删除、覆盖、发布等操作

## 三、必须执行

1. 动手前先说明计划：要改哪些文件、影响什么范围
2. 修改前先 Read 目标文件，不凭记忆改写
3. 生成代码遵循 PEP 8 + Django MVT + 项目命名规范（见 development-guide.md）
4. 每段代码给出可运行/可验证的入口；关键逻辑（审批状态机、RBAC）补单元测试
5. 遵守 Git 提交规范：`类型(范围): 描述`（feat/fix/docs/refactor）
6. 需求或架构变更：先更新文档，再改代码
7. 每阶段完成"可插拔自检"：停掉刚改的插件 → 系统照常跑 → 导航消失
8. 外部事实与数据必须附可追溯来源，区分"已查证"与"推测"

## 四、安全与合规

1. 不得在代码、文档、对话中泄露密钥、Token、数据库密码等敏感信息
2. 不得生成 SQL 注入、XSS、CSRF 等不安全代码；发现即修
3. 涉及数据的操作最小化、可审计；未知数据不按零值或猜测处理

## 五、工作流约束（AI 参与时的分工）

| 阶段 | AI 可自主做 | AI 必须请示 |
|---|---|---|
| 需求 | 整理、提问、结构化输出 | 变更功能范围 |
| 架构 | 提出方案、对比选项 | 改变已定架构 / 技术栈 |
| 编码 | 写代码、修 bug、补测试 | 新增依赖、跨模块设计 |
| 验证 | 跑测试、自检、修复失败项 | 判定"验收通过" |
| 部署 | 编写部署脚本、Docker 配置 | 执行上线 / 发布操作 |

## 六、质量控制

1. 每次 AI 改动后：运行测试或手动验证 → 通过才算完成
2. AI 自己指出的问题未修复前，不得宣称完成
3. 文档与代码不一致时：先以文档为基线确认，再决定改文档还是改代码，禁止两边各说各话
4. 同一动作失败两次须换方案，不得原样重试

## 七、迭代规范（版本迭代流程）

### 7.1 版本规划（语义化版本）

- 版本号遵循 SemVer：`主版本.次版本.修订`
- 里程碑对应版本：

| 版本 | 内容 | 验收门 |
|---|---|---|
| v0.1.0 | 插件容器 plugin_host | 登录页可访问 —— ✅ 已完成（2026-10-21）|
| v0.2.0 | auth + user（RBAC 地基） | 建角色/分配权限/越权拦截 —— ✅ 已完成（2026-10-21）|
| v0.3.0 | approval 审批中心 | 发起→审批→归档闭环 —— ✅ 已完成（2026-10-21）|
| v0.4.0 | notice 公告 | 已读统计正确 —— ✅ 已完成（2026-10-21）|
| v0.5.0 | attendance 考勤 | 看板数据正确 |
| v0.6.0 | blockchain 留痕 | 篡改检测报警 |
| v1.0.0 | 整合 + 部署 + 发布 | 验收标准全过 |

### 7.2 标准迭代循环（每版本）

```
规划 → 开发 → 自检 → 评审 → 发布
```

1. **规划**：确认需求/变更 → 先更新文档（约束/指南）→ 拆分任务清单
2. **开发**：按 development-guide.md 流程（models → migrate → services/views → 模板）
3. **自检**：单元测试 + 可插拔自检（停插件 → 系统照常跑 → 导航消失）
4. **评审**：代码 review；AI 生成代码必须经人审后才合入
5. **发布**：打 tag + 更新 CHANGELOG + 部署验证

### 7.3 变更管理

- 需求/架构变更：**先更新文档，再改代码**；涉及约束变更须负责人确认
- 变更影响评估：列出受影响的插件、文档、测试
- 禁止范围蔓延：对照"必不做"清单，超规模功能移入 Roadmap
- 一个迭代只聚焦一个主题，不夹带无关改动

### 7.4 发布门禁（Definition of Done）

每个版本发布前必须全部满足：

- [ ] 功能验收清单通过（见 constraints-and-acceptance.md）
- [ ] 新增功能有单元测试且通过
- [ ] 可插拔自检通过
- [ ] 文档已同步（README / 开发指南 / 相关规范）
- [ ] CHANGELOG 已记录
- [ ] tag 已打、部署验证通过

### 7.5 AI 在迭代中的角色

- 每轮迭代由负责人定义目标，AI 按"五、工作流约束"分工表执行
- AI 不得自行开启新迭代、扩大迭代范围、夹带无关改动
- 版本判定（能否打 tag、是否达到 v1.0）只能由负责人确认
